# ControlHub: Controlled Job Pipeline & Command Execution

## 1. Controlled Job Model Principles

> [!WARNING]
> ControlHub **never** opens an unauthenticated raw shell port (like SSH or telnet) on an endpoint. All commands follow a strictly validated, queued, and auditable job pipeline.

```mermaid
sequenceDiagram
    autonumber
    actor Admin as Admin Console
    participant API as API Service
    participant Queue as Redis Queue / PostgreSQL
    participant Worker as Dispatch Worker
    participant Agent as Windows Agent

    Admin->>API: POST /devices/{id}/commands {type: "RESTART", delay: 30}
    API->>API: 1. Authentication & Session Check
    API->>API: 2. Granular RBAC Check ('device.restart')
    API->>API: 3. Tenant Boundary & Device Ownership Validation
    API->>API: 4. Policy Check (e.g., Is reboot allowed during business hours?)
    API->>API: 5. Generate Nonce & Expiration Timestamp (Replay Protection)
    API->>Queue: 6. Insert Command Job (Status: 'QUEUED')
    API-->>Admin: 202 Accepted {command_id: "..."}

    Worker->>Queue: Dequeue Next Job
    Worker->>Agent: Dispatch over TLS WebSocket with Signature & Nonce
    Agent->>Agent: 7. Validate Nonce freshness & cryptographic signature
    Agent->>Agent: 8. Execute in isolated Windows process (Capture Stdout/Stderr)
    Agent-->>Worker: 9. Report Result {exit_code: 0, stdout: "...", duration_ms: 320}
    Worker->>Queue: 10. Update command_results table (Status: 'SUCCESS')
    Worker->>API: 11. Write Immutable Audit Log
    API-->>Admin: Stream Result to Console UI via WebSocket
```

## 2. Replay Protection & Cryptographic Command Signing

Every command dispatched to an endpoint carries:
1. **`command_id`**: Unique UUIDv4.
2. **`issued_at` & `expires_at`**: Strict time window (commands expire in 5 minutes if offline).
3. **`nonce`**: Single-use random 128-bit value; endpoints cache recent nonces to prevent replay attacks.
4. **`payload_signature`**: HMAC-SHA256 or Ed25519 signature generated by the platform secret, verified by the agent before spawning any subprocess.

## 3. Safe Bulk Management Workflow

Bulk operations across hundreds of workstations (such as classroom restarts, software updates, or mass shutdowns) carry high operational risk if misconfigured. ControlHub enforces a **multi-stage confirmation gate**:

```mermaid
graph TD
    Step1[1. Admin selects Group or Multi-Device Checkboxes]
    Step2[2. Admin selects action: e.g. 'Bulk Restart']
    Step3[3. Modal Displays: Exact List of Target Machines with Status & Warnings]
    Step4[4. Admin must type target count or explicit confirmation word e.g. 'RESTART 35 COMPUTERS']
    Step5[5. Backend decomposes bulk request into atomic, isolated jobs]
    Step6[6. Worker queues jobs with staggered dispatch rate to prevent network storms]
    Step7[7. Progress bar streams live success/failure counts to Admin Console]
    Step8[8. Audit record created with total targeted, succeeded, and failed counts]

    Step1 --> Step2 --> Step3 --> Step4 --> Step5 --> Step6 --> Step7 --> Step8
```

### Safety Protections:
- **Never Silent**: Bulk disruptive actions cannot be executed with a single click.
- **Staggered Dispatch**: Commands are dispatched with a configurable throttle (e.g. 10 devices per second) to avoid overwhelming local network switches or domain controllers.
- **Active User Warning**: If an interactive user is logged on, the command can automatically notify the user with a countdown dialog before restarting.
